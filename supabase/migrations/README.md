# Aplicar migraciones de activación y operación cloud

1. Haz un respaldo verificable de Supabase y aplica `202610290001_atomic_tenant_activation.sql` primero en un proyecto de prueba.
2. Revisa y prueba las funciones de activación antes de aplicarlas a producción. La migración se detiene si encuentra códigos de emparejamiento duplicados o más de una licencia activa por tenant.
3. Si ya ejecutaste el SQL manual compartido, corre primero `supabase/hotfix_revoke_unsafe_anon_policies.sql` en SQL Editor. Sus políticas permitían leer tenants/dispositivos completos e insertar dispositivos anónimamente.
4. Aplica en orden `202610290002_console_operator_auth.sql` y `202611020001_mobile_admin_catalog_policies.sql`.
5. Antes de `202611030001_cloud_first_waiter_orders_reports.sql`, busca y resuelve mesas duplicadas por tenant/nombre, meseros básicos duplicados por tenant/nombre y más de una comanda abierta o por cobrar por mesa. La migración aborta si detecta esos casos.
6. Después de la migración cloud-first, aplica `202611030002_fix_waiter_pgcrypto_search_path.sql` (incluye el RPC de restablecimiento de PIN) y luego `202611030003_resolve_pgcrypto_schema.sql`. Esta última detecta el esquema real de `pgcrypto`, prueba un hash temporal y configura las funciones con ese esquema.
7. La migración cloud-first conserva el ingreso por restaurante, nombre y PIN. Después de validar el PIN, emite automáticamente una sesión opaca para autorizar las operaciones siguientes; el mesero no ingresa un dato adicional. También guarda hashes de los PIN, agrega unicidad para mesas y comandas activas, y hace transaccionales las comandas/cobros. Verifica inicio de sesión de mesero, aislamiento entre tenants, concurrencia de mesas, cobros y reportes antes de producción.
8. El registro y licenciamiento de dispositivos en la nube se conserva. Se retiraron el servidor TCP local, su pairing Wi-Fi y la dependencia `react-native-tcp-socket`; ventas y comandas requieren conectividad con Supabase.
9. Si existe una fila en `platform_operators`, `/setup` no crea otra cuenta. Usa la cuenta existente solo después de verificar Auth y cambiar la contraseña filtrada. Para cuentas nuevas, configura `SUPABASE_SERVICE_ROLE_KEY`, `CONSOLE_OWNER_EMAIL` y `CONSOLE_BOOTSTRAP_SECRET` únicamente si aún no hay propietario.
10. Nunca uses prefijo `NEXT_PUBLIC_` para secretos. El ingreso regular está en `/login`; el propietario administra las cuentas adicionales en `/operators`.
